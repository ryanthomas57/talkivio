# Talkivio threat model

Master prompt ch. 52 (threat model and controls), with ch. 04 (tenant isolation), ch. 19 (files),
ch. 27 (widget security), ch. 53 (privacy) and ch. 55 (webhooks). Code paths are relative to the
repository root. "Test / evidence" names the automated check that exercises the control today; where
none exists the row says so. Status values: **verified** (automated test passes in CI / locally),
**partial**, **not verified**.

> **Manual review:** ch. 52 requires a documented manual review of authorization paths and exports;
> automated scanners passing is insufficient. That review has **not been performed yet** — this
> document is the input to it, not its result. Owner: Security lead. Until it is done, no row is
> considered closed for release purposes (see AUD-72-10 in [`docs/release-audit.md`](../release-audit.md)).

## 1. Assets

| Asset                                         | Where it lives                                                                                                                     | Why it matters                                             |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Transcripts (public messages, internal notes) | `messages`, exports in object storage, search index (GIN FTS on `messages.body`)                                                   | confidentiality between tenants and between staff/visitors |
| Visitor identity and personal data            | `visitors` (email ciphertext + lookup hash), `visitor_identities`, sessions, consent records, page events                          | privacy obligations, erasure                               |
| Authentication material                       | `auth_sessions` (hashed tokens + CSRF hash), `auth_tokens`, MFA secrets (encrypted), socket tickets in Redis, visitor capabilities | account takeover                                           |
| Integration secrets                           | `integration_credentials` (hashed API tokens), webhook signing secrets (encrypted), OAuth/billing keys                             | lateral access to customer systems                         |
| Attachments                                   | quarantine and clean buckets                                                                                                       | malware distribution, data leakage                         |
| Tenant configuration                          | sites, origins, schedules, triggers, widget config revisions                                                                       | defacement, routing abuse                                  |
| Billing state                                 | `billing_accounts`, `billing_events` (optional module)                                                                             | fraud                                                      |
| Platform secrets                              | `APP_SECRET` (encryption + HMAC key), database/Redis/S3/SMTP credentials                                                           | full compromise                                            |
| Erasure ledger                                | `exports/privacy-ledger/…` objects, `subject_tombstones`                                                                           | prevents resurrection of erased data after restore         |

## 2. Attacker classes

| ID  | Attacker                        | Capability assumed                                                                       |
| --- | ------------------------------- | ---------------------------------------------------------------------------------------- |
| A1  | Anonymous spammer               | scripts the public widget API and sockets at volume, any origin header from non-browsers |
| A2  | Malicious visitor               | controls their browser and widget session; sends crafted messages, files, SDK calls      |
| A3  | Malicious agent                 | valid staff account with limited role in one tenant                                      |
| A4  | Compromised tenant admin        | full admin of one tenant; wants another tenant's data or platform control                |
| A5  | Stolen session                  | holds a staff cookie or socket ticket or visitor capability                              |
| A6  | Hostile embedding origin        | a website that is not an approved origin embeds the loader or frames the widget          |
| A7  | Compromised webhook destination | controls an endpoint URL / DNS of a configured webhook                                   |
| A8  | Infrastructure operator         | access to hosts, backups, logs or CI                                                     |

## 3. Trust boundaries and entry points

```
 [Host page (any origin)] --loader.js--> [Widget iframe @ API origin] --REST /widget/v1, WS /realtime/v1 (visitor ns)--+
 [Agent browser @ APP_URL] --cookie+CSRF REST /api/v1, WS /realtime/v1 (agent ns), ticket in CONNECT frame-----------+
                                                                                                                     v
 ===================================== edge: TLS 1.2+, reverse proxy, WAF/rate limits ===================================
                                                                                                                     v
                 api / gateway (validate schema + permission on every command, derive tenant server-side)
                     | RLS-bound DB role                 | Redis (tickets, presence, queues)    | S3 (quarantine/clean)
                     v                                   v                                      v
 ================ private network: PostgreSQL 16 (RLS) · Redis · object store · ClamAV ===========================
                     ^
                 worker -> SMTP relay (outbound) · webhook endpoints (outbound, SSRF-guarded) · provider callbacks (inbound, signed)
```

Boundaries: B1 host page ↔ widget iframe (postMessage), B2 browser ↔ edge (REST/WS), B3 app ↔ database
(RLS), B4 app ↔ Redis, B5 app ↔ object store/scanner, B6 worker ↔ external SMTP/webhooks/providers,
B7 CI/build ↔ runtime (supply chain), B8 operators ↔ production data (backups, logs).

## 5. Infrastructure controls (ch. 52)

- TLS 1.2+ terminates at the edge (production); local Compose is HTTP on loopback only.
- Database and object store on private networks; Compose models this with an `internal: true` network;
  only explicitly listed dev ports are published, bound to 127.0.0.1.
- Least-privilege credentials per component: `talkivio_app` (DML under RLS) for services,
  `talkivio_owner` only for migrations, MinIO application user limited to two buckets, Redis password.
- Containers: non-root, read-only root filesystem where feasible, dropped capabilities, resource limits,
  tini as PID 1, `HEALTHCHECK` on `/health/live`.
- CI: dependency and secret scanning, SBOM, image scanning; provenance/signing pending a registry.
- No production secrets in seed fixtures (the seed refuses `NODE_ENV=production` and reads only
  documented local placeholders), build args or source maps.
